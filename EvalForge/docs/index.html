EvalForge

Regression tests for LLM apps, scored by an AI judge and enforced in CI

Prompts, models and providers change underneath every LLM product. EvalForge runs a suite of test questions on every push, has a second model grade each answer, and blocks the change if quality drops. This page is its live output.

Engineering

Design decisions

An eval is only useful if you can trust it. These are the parts that make it trustworthy.

An independent, validated judge

A different model family grades the answers, so the model never grades itself. Every verdict is parsed into a Pydantic model and retried with the parse error on failure.

Failures can't hide

A test that errors (rate limit, outage, retired model) fails the gate. A broken provider can never show up as "no regressions".

Built for rate limits

Test cases fan out with asyncio.gather under a semaphore. Rate-limited calls wait out the provider's token window and retry instead of failing the run.

Runs fully offline

Demo mode swaps in a deterministic mock for both model and judge, so the whole pipeline runs with no API keys or database. CI runs it before the live suite.

Fails fast on bad config

Provider, API keys and database are validated at startup, with a one-line error instead of a stack trace halfway through a run.

Judge noise is measured

The same answer can score 0.5–1.0 apart between runs. The chart shows it, and the baseline is picked from a typical run, not a lucky one.
